## New findings

### [MAJOR] A. The plan gives contradictory instructions when drops exist but `measurement` is not `"full"` — and the once-per-instance epoch flag makes that state permanent
- **Where**: `01-store-dedupe-counter.md` §"Counting-start epoch" (bullets 4–6) and criterion 01.10; `02-reconcile-aggregation.md` requirement 4 (`measurement` derivation); `03-reconcile-output.md` §"Always-printed defect sections" (`DEDUPE DROPS` states 1–2 vs the `--daily` sub-table bullet) and criteria 03.5, 03.11.
- **Problem**: `by_type` can be non-empty while `measurement` is `"none"` or `"partial"`, by two independent routes.
  - *By design*: `01` §Schema requires `day` to come from "the dropped datapoint's own timestamp ... NOT from wall-clock now", so a replayed old export counted today records drops dated inside a window that entirely precedes the epoch. `02` requirement 4 maps that to `measurement == "none"` (`epoch_day >= end`).
  - *Newly introduced*: the epoch write "must never raise into the caller" and must not `commit()`, so it lives in the caller's transaction — and `receiver.py`'s transcript path calls `store.db.rollback()` then re-raises on any non-`_RECORD_DATA_ERRORS` exception (verified at `receiver.py:379-387`; its own docstring calls `sqlite3.OperationalError` "database is locked"/"disk I/O error" *ordinary conditions on a single-host SQLite deployment*). The receiver holds one long-lived `OtelStore` (`receiver.py:511`). If the first request of the process is rolled back, the epoch write is discarded while the in-memory flag stays latched, so the epoch is never re-attempted for the process lifetime. `dedupe_epoch()` returns `None` forever while drops from later successful requests commit normally. `01` never says whether the flag is set on attempt or only after a write known to be committed, and criterion 01.10 ("asserting exactly one" `SELECT ... FROM meta` across ten inserts) actively forbids the re-check that would recover.
  Task 03 then instructs both "Print no count" (states 1 and 2) and, four bullets later, that `--daily` "additionally renders `dedupe_drop_report(...)["by_day"]` as a per-day sub-table", with criterion 03.11 requiring that sub-table "when drops exist". Those cannot both hold.
- **Consequence**: reconcile prints "counting has never run against this database" while suppressing a real, non-empty duplicate count — the precise silent failure this goal exists to eliminate, now in the new code path. The implementer of task 03 must pick one of two instructions that contradict each other inside their own task file, with no guidance, and the trade the flag buys is one primary-key lookup on a one-row `meta` table per request against a permanently-wrong epoch.
- **Fix**: three narrow edits. (1) `01`: state that the in-memory flag may be set only after an epoch write that the caller has committed, or drop the once-per-process guarantee to once-per-request and relax criterion 01.10 to "at most one `meta` lookup per insert *batch*" — the cheaper and safer option. (2) `02` requirement 4: add a `"counts_outside_measurement": bool` (or equivalent) that is `True` when `by_type` is non-empty and `measurement != "full"`, so the inconsistency is in the return value rather than inferred. (3) `03`: state that a non-empty `by_type` is **always** printed, with the measurement wording as a qualifier rather than a substitute — "counting began after this window, yet N drops dated in it were recorded (replayed export or an interrupted first write)" — and reconcile the `--daily` sub-table bullet with states 1–2 explicitly. Add a criterion covering non-empty `by_type` under each of states 1–3.
