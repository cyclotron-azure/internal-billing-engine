## Summary

The decomposition, ownership contracts, and constraint propagation are genuinely strong — write fences are disjoint-or-ordered, the contract-first ordering is right, and the epoch/labeling decisions from Phase 1 are all carried into tasks. But the plan is not executable as written by zero-history implementers: the `--daily` feature has no day-key format contract (the one truth source that differs, `usage_report`'s `starting_at`, is an RFC3339 timestamp that nothing in the plan truncates), task 02's three Analytics acceptance criteria name a mocking seam that provably cannot work, and roughly half of task 02/03's `billing/reconcile.py:NN` citations point at different code than they claim — including one that tells the implementer to leave unchanged the exact lines the task requires changing. The single biggest risk is the day-key mismatch: it would ship a `--daily` table where every day appears twice, once with truth and `0` captured, which reads exactly like the receiver-outage signal this goal exists to create.

Baseline verified green before scoring: `python -m pytest tests/test_otel_store.py -q` → `27 passed in 2.36s`.

## Findings

### [MAJOR] `analytics_claude_code_daily`'s day-key format is unspecified, and the one source that differs is the org-wide truth side  (risk #3, #6)
- **Where**: `02-reconcile-aggregation.md` requirement 3 (`analytics_claude_code_daily(start, end) -> dict[str, dict]`, "using the `(day, row)` pairs `client.usage_report(...)` already yields"); `03-reconcile-output.md` `--daily` ("union of days present in truth and in captured").
- **Problem**: Three day sources feed the union and only two are pinned. `otel_daily` derives days from `substr(ts,1,10)` → `YYYY-MM-DD`. `analytics_user_daily` reads `user_cc_usage.day`, which `billing/store.py:50-51` (`_day(iso) = (iso or "")[:10]`) already truncated to `YYYY-MM-DD`. But `analytics_client.py:129` yields `bucket.get("starting_at")` verbatim from the API payload — the value `billing/store.py`'s `_day()` helper exists precisely to truncate, and which `ingest.py:39` passes through that helper on every write. Task 02 never says to truncate it; task 03 never states the key format it renders. `dedupe_drops_by_day` (task 01) is a third shape (`YYYY-MM-DD`) with no stated relationship.
- **Consequence**: If `starting_at` arrives as `2026-07-14T00:00:00Z`, the union of truth days and captured days is disjoint, so `--daily` prints every day twice — once with truth and zero captured (indistinguishable from a receiver outage) and once with captured and zero truth. This is the marquee new section, in the module invoices are built on. Even if the API happens to return a bare date, the contract is unpinned and an implementer can satisfy the task text either way.
- **Fix**: State in task 02 requirement 3 that every day key in every new function is exactly `YYYY-MM-DD`, and that `analytics_claude_code_daily` must normalize `usage_report`'s yielded `starting_at` with the `[:10]` truncation (reuse `billing.store._day` or restate it). Add an acceptance criterion pinning a key literal (e.g. a fake payload yielding `"2026-07-14T00:00:00Z"` produces the key `"2026-07-14"`).

### [MAJOR] No criterion requires per-day figures to reconcile with the period totals  (risk #7, #8)
- **Where**: `02-reconcile-aggregation.md` Acceptance Criteria 1–11; `03-reconcile-output.md` Acceptance Criteria 1–14.
- **Problem**: Criterion 02.4 pins the *surface* invariant (each dimension sums to `captured_total`), but nothing pins the *temporal* one: `sum(otel_daily(...) captured per day) == sum(otel_totals(...)["captured"])`, and the same for truth. That single assertion is what catches the day-key defect above, any half-open-window slip, and any `GROUP BY` that silently drops rows with a NULL grouping column.
- **Consequence**: A `--daily` table whose rows do not add up to the `BY TOKEN TYPE` total ships undetected, and the two numbers appear on the same page for the same window. A reviewer comparing them against an invoice gets two different answers.
- **Fix**: Add to task 02 a criterion: for a fixture spanning three days, `Σ_day otel_daily[day]["captured"][k] == otel_totals[...]["captured"][k]` for every `k` in `CANON`, and the same identity for `analytics_claude_code_daily` vs `analytics_claude_code_totals` and `analytics_user_daily` vs `analytics_user_totals`.

### [MAJOR] The measurement epoch records when the schema was migrated, not when counting began  (risk #5, #6)
- **Where**: `01-store-dedupe-counter.md` "Measurement epoch" ("In `_migrate()`, if that key is absent, set it to the current UTC date"); `02-reconcile-aggregation.md` requirement 4 (`measured = False` when `epoch is None or epoch > start`).
- **Problem**: `_migrate(self.db)` runs on **every** `OtelStore` construction (`otel_store.py:241`), and ten call sites open `OtelStore` — `reconcile.py:130`, `bill.py:60`, `export.py:175`, `invoice.py:193`, `fabric_sync.py:79`, `records.py:20`, `repos.py:30,50`, `scheduler.py:72`, `receiver.py:511`. Whichever process opens the database first after deploy writes the epoch, and the epoch is "written once, ever". If an operator runs `python -m billing.reconcile` or `bill.py` on the new code on day X while the receiver is still running the *old* code (no restart yet), the epoch is stamped X even though no drop is counted until the receiver restarts on day X+3.
- **Consequence**: The window `[X, X+3)` then satisfies `epoch <= start`, so task 03 renders case 2 — "there were no duplicate datapoints in this window" — for a window in which drops were never counted. That is exactly the misleading `0` the epoch mechanism exists to prevent, arrived at by a different route. Secondarily, this makes every read-only consumer perform a write on first open; a `sqlite3.OperationalError: database is locked` there propagates out of `_migrate()` and takes the opening process down, which the task's own "a migration that raises on open takes the receiver down" warning is about.
- **Fix**: Write the epoch from a path that implies the counting writer is live — a `OtelStore.ensure_dedupe_epoch()` (or equivalent) called once from `receiver.py`'s startup, or lazily on the first increment attempt — rather than from `_migrate()`. If the plan keeps it in `_migrate()`, task 01 must state the deploy ordering as a hard requirement (restart the receiver on the new code *before* any other process opens `otel.db`) and task 03's wording must not imply "counting began" when it means "schema migrated". Also require `_migrate()` to tolerate a failed epoch write rather than raise.

### [MAJOR] The share-of-captured invariant has no runtime visibility  (risk #7)
- **Where**: `02-reconcile-aggregation.md` criterion 4; `03-reconcile-output.md` `--by-surface`.
- **Problem**: The labeling half of risk 7 is well handled — task 03 mandates the header say "share of captured, NOT coverage", and criterion 10 asserts both literal strings, so the mislabeling is genuinely hard to ship. The *arithmetic* half is not: the "each dimension sums to `captured_total`" invariant lives only in a fixture unit test. Nothing in the rendered output lets a reader see that a dimension stopped summing to 100% — no sub-block total, no residual row.
- **Consequence**: A dimension that gains a value the query drops (a NULL grouping column, a value filtered by a future predicate) prints a set of percentages that look like they should sum to 100% and do not, on the page a reviewer reads next to an invoice. The fixture test cannot catch a data shape the fixture does not contain.
- **Fix**: Require each `--by-surface` sub-block to print its own `TOTAL` row with `ftok` + exact integer + `pct(block_total, captured_total)`, and require that percentage to read `100.00%`. Add the corresponding acceptance criterion to task 03 (assert the literal `100.00%` on each of the three sub-blocks).

## Devil's advocate (required by `goal-criteria` §6)

1. **Steelman the strongest alternative**: skip the `dedupe_drops` table entirely and make `dp_key` collision-free instead — the three silent causes reduce to two, and a counter measuring a defect you could have eliminated is instrumentation debt. The plan's own `transcript_key` docstring (`otel_store.py:156-197`) is the precedent: a collision was fixed structurally, not counted. The goal's counter-argument holds (OTLP `dp_key` collisions are not obviously eliminable without a `request_id` column, which is explicitly out of scope and deferred to roadmap Phase 1), but that reasoning is not written down in `goal.md` and should be.
2. **Load-bearing assumptions treated as fixed**: (a) that `usage_report`'s `starting_at` is a usable day key — finding 1; (b) that duplicates are "by definition rare" — a retried OTLP export re-sends the whole batch, making *every* datapoint in it a duplicate, so the collision path is bursty rather than rare (the cost stays bounded only because the bucket table is at most a few rows per day, keyed by PK); (c) that whoever migrates the database is the process that counts — finding 5; (d) that `epoch` at date granularity is precise enough — the epoch day itself is a partially-measured window that renders as fully measured.
3. **30-day pre-mortem**: the most likely failure is a `--daily` table that nobody trusts, because per-day rows do not add up to the period total (finding 1 plus the missing invariant in finding 2), and the second most likely is a `DEDUPE DROPS: no duplicate datapoints in this window` line for a window that predates the receiver restart (finding 5). Both are "the diagnostic lied", which is worse than the opaque single percentage the goal set out to replace.
4. **Concrete alternative sketch**: emit the diagnostics as one `DIAGNOSTICS` block computed from a single combined aggregation function returning `{period, by_day, by_surface, unmapped, dedupe}` with one invariant-check helper that asserts internal consistency (Σdaily == period, Σdimension == captured_total) and prints a `!! INTERNAL INCONSISTENCY` line when it fails. Same output, but the funnel polices itself instead of relying on fixture tests. Worth adopting the invariant helper even if the rest of the shape stays as planned.
5. **Risks the goal implicitly accepts**: no per-surface truth denominator ever (explicit and correct); dedupe drops unmeasurable before the epoch (explicit and structurally true); no request-grain reconciliation (deferred); and — not stated — that `otel_by_surface` and `otel_daily` add two more full passes over the correlated-subquery `resolved_view`, so `reconcile.py`'s runtime roughly triples on a large `token_usage`.
